## 평가 대상

- 기준 사진은 판정에서 "같은 장소인지" 비교에만 쓰인다(photo-verification spec). 그래서 장소가 정해진 미션만 대상으로 한다. "노란색 찾기"처럼 장소가 정해지지 않은 미션은 제외한다.
- 미션은 현재 Maru DB의 공용 미션에서 고른다. 고른 미션 id를 데이터셋 라벨에 적는다.

## 데이터셋

미션마다 기준 사진 2~4장과 제출 사진 10장 안팎을 둔다. 제출 사진에는 기대 결과를 붙인다.

| 종류 | 기대 결과 | 미션당 장수 |
| --- | --- | --- |
| 같은 장소 (조명·각도·계절이 다름) | pass | 3~4 |
| 다른 장소 (비슷해 보이는 곳 포함) | retry | 2~3 |
| 장소가 애매한 직접 촬영 사진 | pass (애매하면 통과) | 1~2 |
| 화면 캡처·그림·내려받은 이미지 | retry | 1 |
| 얼굴 정면·번호판이 보이는 사진 | privacy | 1 |

- 라벨 파일(`dataset.json`)에 파일 이름, 미션 id, 종류, 기대 결과, 출처를 적는다. 사진은 저장소 밖 폴더에 두고 스크립트에 경로로 넘긴다.
- 기준 사진과 제출 사진은 서로 다른 사진이어야 한다. 같은 사진을 쓰면 장소 비교가 아니라 이미지 일치를 재게 된다.

`dataset.json` 형식(`eval.mjs`가 읽을 때 검사한다. 종류와 기대 결과가 위 표와 다르거나, 기준 사진과 같은 파일이 제출 사진에 있으면 멈춘다):

```json
{
  "missions": [
    {
      "id": "<미션 id>",
      "title": "<미션 제목>",
      "verify_hint": "<인증 힌트>",
      "references": [{ "file": "ref-1.jpg", "hint": "정문 쪽에서 본 모습", "source": "<출처 URL>" }],
      "submissions": [
        { "file": "same-1.jpg", "kind": "same", "expected": "pass", "source": "<출처 URL>" }
      ]
    }
  ]
}
```

`kind`는 `same`·`other`·`ambiguous`·`capture`·`privacy` 중 하나다.

## 평가 스크립트

- `tests/helpers/load-source.mjs`로 `verify-mission`을 불러온다(단위 테스트와 같은 방식). DB와 Storage는 가짜로 넣는다.
  - 가짜 DB는 데이터셋의 제출 사진과 기준 사진을 돌려주고, 결과 저장(`finish_verification`)은 기록만 하고 쓰지 않는다.
  - AI 호출(`generateJson`)은 실제 `_shared/ai.ts`를 쓰고 Gemini 키는 환경 변수로 받는다.
- 이렇게 하면 운영 함수와 같은 프롬프트·판정 코드를 쓰면서 운영 DB에는 아무것도 남지 않는다.
- 조건 A는 기준 사진 0장, 조건 B는 등록할 기준 사진을 넣는다. 나머지는 같다.
- 사진마다 결과, 응답 시간, 판정 문구를 CSV로 남긴다. 같은 사진의 결과가 흔들리는지 보려고, A와 B가 다르게 나온 사진만 3번 다시 돌린다.

## 지표와 운영 등록 기준

- 정확도: 기대 결과와 같은 비율
- 잘못 거절한 비율: 기대 pass인데 retry. "애매하면 통과" 원칙상 가장 중요하다.
- 잘못 통과시킨 비율: 기대 retry인데 pass
- 개인정보 판정 비율: 기대 privacy인데 privacy
- 응답 시간: 중앙값과 가장 느린 값 (20초 시간 초과에 얼마나 가까운지)

운영 등록 기준: 조건 B가 A보다 잘못 거절한 비율이 늘지 않고, 다른 장소를 가려내는 비율(다른 장소 사진의 retry 비율)이 오르고, 응답 시간이 시간 초과에 걸리지 않는다. 미션별로 판단해 기준을 넘은 미션에만 등록한다.
